# Ampere dataflow

Ampere produces synthetic source data in PostgreSQL and publishes analytical Iceberg tables in Lakekeeper. Contract v6 captures exact mutation-time row images as immutable typed Parquet in MinIO, then transfers them into Raw Iceberg and reconstructs Bronze from each frozen accepted history boundary. This checkout contains the implementation; release and live rebuild status are tracked in `.local/current_steps.md`.

After a successful Gold publish, the Curie refresh DAG requests a FlightSQL cache refresh through `/api/cache/refresh_flightsql`, then polls the Iceberg cache status until a new release is active.

## Layers

1. **Source:** Python generators create orders, clients, products, payments, delivery activity, and costs in PostgreSQL.
2. **Raw:** Init and generators capture typed INSERT, UPDATE, DELETE, and baseline rows at mutation time into bounded immutable MinIO Parquet. PostgreSQL holds compact dataset/batch controls, not row events. Spark validates committed manifests, merges them into the separate Raw Lakekeeper warehouse, and acknowledges each table only after its Iceberg commit. A stable transfer identity makes commit-before-ack retries idempotent.
3. **Bronze:** Daily Spark applies version-guarded changes by dataset ID and stable source-row ID. Full rebuild computes each mutable table's latest operation across the complete frozen history, then replaces the whole Iceberg table in one commit. Proven insert-only `order_product` rows use a direct bulk write. Both jobs run snapshots/mutable dimensions first, then facts/events in separate Spark applications; the second application advances the PostgreSQL transfer checkpoint only after all table acknowledgments exist.
4. **Silver:** An isolated dbt/DuckDB pod stages, cleans, joins, tests, and publishes reusable entities.
5. **Gold:** A separate dbt/DuckDB pod reads published Silver tables and publishes sales, delivery, cost, and margin marts.
6. **Serving:** Curie refreshes its cache after successful Gold publication.

## Orchestration and recovery

The scheduled generator and Raw tasks hand off to Bronze only. The manual `ampere__pre_raw__generators__backfill` DAG accepts an inclusive date range without a day-count cap and generates dates sequentially in one node4 pod. Source and compact batch controls commit one calendar month at a time, while daily generation keeps one transaction per date. Mutation helpers stream exact row images to bounded staging files as writes happen. A failed month rolls back as a unit; completed months remain and are skipped on retry. The DAG and task have eight-hour timeouts. Backfill triggers no downstream DAG. Raw transfer uses PostgreSQL's indexed per-dataset batch high-water mark and processes only later batches. `max_batches` sets the total per Airflow run (default 32); `batch_size` bounds each sequential transfer group to at most 96. Silver, Gold, and Curie automatic handoffs stay disconnected. Raw, Bronze, catalog initialization, publication, and housekeeping share the one-slot Airflow pool `iceberg_pipeline_mutation`. [The DAG inventory and trigger graph](dataflow/generated/airflow_dag_orchestration.md) shows the handoffs.

Live node4 readings show 6 allocatable CPUs, about 13.5 GiB allocatable memory, and no memory or disk pressure. Existing pods request 2.65 CPUs and 2.8 GiB memory. Generator pods request 3 CPUs and 4 GiB memory (limits 4 CPUs and 6 GiB), with Polars capped at 3 threads and BLAS at 1. Init requests 1 CPU and 2 GiB. Bronze runs two sequential applications on node4: snapshots/mutable dimensions use two 1-core executors with 2.5 GiB heap and 2 shuffle partitions; facts/events use two 3-core executors with 3 GiB heap plus 768 MiB overhead, requesting 1.3 CPUs each, and 8 shuffle partitions. Its driver uses 2.5 GiB heap plus 512 MiB overhead. Airflow Variables can tune these profiles. PostgreSQL is on node1 with a 10 GiB PVC and about 0.9 GiB node memory available, so JDBC extraction uses one sequential reader and no parallel range scan. PostgreSQL PVC used space and I/O capacity have not been measured; no journal-size guarantee is claimed. These are DAG settings, not live cluster changes.

The housekeeping client discovers Raw, Bronze, Silver, and Gold tables from contract profiles. Raw change history is retained in Iceberg for rebuilds and audits. Acknowledged MinIO staging payloads are cleaned only after the configured 7–14 day grace period; uncommitted or unacknowledged payloads are retained. Raw transfer records keep per-table Iceberg snapshot IDs; Bronze records a completed dataset boundary and per-table acknowledgments.

Contract v6 requires the Raw Lakekeeper warehouse and MinIO storage access. Catalog initialization creates or validates the 58 contract tables; the manual `ampere__iceberg__bronze__catalog_reset` DAG drops and reinitializes only contract-managed Bronze tables. The drop uses Lakekeeper's managed deletion behavior; physical cleanup follows its retention policy. Run the Bronze full-rebuild DAG after all source batches are accepted. It reads only accepted Raw batches through the frozen boundary, uses up to 256 shuffle partitions (targeting about 100,000 raw rows each) and stable source-row hash buckets for bounded latest-state reduction, stages the result in temporary Parquet, and atomically overwrites each table once. It preserves the two sequential Spark applications and current two-executor resource profiles. Keep Silver, Gold, and Curie handoffs disconnected.

The daily publisher stages and tests models locally before changing Lakekeeper tables. Silver daily `fact_delivery_tracking` and `fact_order_product` inputs publish through three `order_id` ranges each, with keyed `MERGE` updates and inserts; target-only historical rows are preserved. Complete Silver dimensions and budgets use a keyed merge followed by deletion of keys absent from the complete source. Every Gold dbt model reads the full published Silver inputs and produces a complete aggregate snapshot in daily and full-history modes. Gold publication updates and inserts its keys, then removes keys absent from that snapshot. Empty complete sources fail before publication. Fact ranges commit independently, so a failed publish can leave earlier ranges applied; rerunning the DAG converges by replaying all ranges.

Silver and Gold layouts follow DuckDB Iceberg 1.5 write limits: they are unsorted, and Silver fact partitioning uses DuckDB-supported identity transforms. For partitioned writes DuckDB ignores the target-file-size property; weekly Spark housekeeping uses the contract size target when compacting those tables. Contract validation rejects Spark-only distribution modes and unsupported DuckDB transforms before initialization.

## Contract and catalog

[The canonical Iceberg contract](../tools/contracts/ampere_tables.json) contains v6: 16 Raw, 17 Bronze, 17 Silver, and 8 Gold tables. It defines Raw event keys, entity keys, operation semantics, source order, typed Parquet staging, physical layouts, publication keys, and maintenance profiles. `tools/contracts/ampere_contract.py` validates and resolves these fields, and Spark conformance checks active partition and sort metadata. Bronze's current-state lineage includes dataset ID, stable source-row ID, batch sequence, and change ID. dbt models still define Silver and Gold transformations and tests.

To regenerate the diagrams and DAG inventory, run `uv run python tools/docs/generate_dataflow_docs.py` from the repository root.
