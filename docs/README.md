# Ampere dataflow

Ampere produces synthetic source data in PostgreSQL and publishes analytical Iceberg tables in Lakekeeper. Task 6 now has a local v4 implementation for transactional source journaling, idempotent Raw transfer, and incremental Bronze state. It has not been released or deployed yet. The current cluster continues to run the previous Raw/Bronze runtime until the owner publishes the coordinated image and DAG changes and completes the source/catalog cutover.

After a successful Gold publish, the Curie refresh DAG requests a FlightSQL cache refresh through `/api/cache/refresh_flightsql`, then polls the Iceberg cache status until a new release is active.

## Layers

1. **Source:** Python generators create orders, clients, products, payments, delivery activity, and costs in PostgreSQL.
2. **Raw:** PostgreSQL captures typed INSERT, UPDATE, DELETE, and baseline rows in the same transaction as source writes. Spark freezes completed batches, merges them into the separate Raw Lakekeeper warehouse, and acknowledges each table only after its Iceberg commit. A stable transfer identity makes commit-before-ack retries idempotent.
3. **Bronze:** Spark reduces each accepted interval in source order and applies rows by dataset ID and stable source-row ID. Updates and deletes retain source sequence guards; a full rebuild reduces all accepted history in one bounded Spark application. PostgreSQL records per-table and global checkpoints.
4. **Silver:** An isolated dbt/DuckDB pod stages, cleans, joins, tests, and publishes reusable entities.
5. **Gold:** A separate dbt/DuckDB pod reads published Silver tables and publishes sales, delivery, cost, and margin marts.
6. **Serving:** Curie refreshes its cache after successful Gold publication.

## Orchestration and recovery

The scheduled generator and Raw tasks hand off to Bronze only. The manual `ampere__pre_raw__generators__backfill` DAG accepts an inclusive date range without a day-count cap and generates dates sequentially in one node4 pod. Source and journal changes commit one calendar month at a time, while daily generation keeps one transaction per date. Statement-level journal triggers capture each SQL write batch set-wise. A failed month rolls back as a unit; completed months remain and are skipped on retry. The DAG and task have eight-hour timeouts. It triggers no downstream DAG inside the date loop. Raw processes at most 32 source batches per run, including the bootstrap batch, and catches up on later runs. Silver, Gold, and Curie DAG definitions remain available for manual use, but automatic handoffs stay disabled until the owner authorizes restoring them. Raw, Bronze, catalog initialization, publication, and housekeeping share the one-slot Airflow pool `iceberg_pipeline_mutation`; this pool must exist before deploying the DAGs. [The DAG inventory and trigger graph](dataflow/generated/airflow_dag_orchestration.md) shows the disabled handoffs.

Live node4 readings during the implementation pass showed 6 allocatable CPUs, about 13.5 GiB allocatable memory, about 44.5 GB free ephemeral storage, and no memory or disk pressure. Resident services used about 5.3 GB working set; metrics-server CPU/memory top was unavailable. Generator pods now request 3 CPUs and 4 GiB memory (limits 4 CPUs and 6 GiB), with Polars capped at 3 threads and BLAS at 1. Init requests 1 CPU and 2 GiB. Raw and Bronze Spark work runs one application at a time on node4; Raw uses at most two executors, Bronze at most three. PostgreSQL is on node1 with a 10 GiB PVC and about 0.9 GiB node memory available, so JDBC extraction uses one sequential reader and no parallel range scan. PostgreSQL PVC used space and I/O capacity have not been measured; no journal-size guarantee is claimed. These are proposed image/DAG settings, not live cluster configuration.

The v4 housekeeping client discovers Raw, Bronze, Silver, and Gold tables from contract profiles. Raw logical change history is retained until explicit dataset retirement; PostgreSQL does not prune journal rows. Raw transfer records keep the per-table Iceberg snapshot IDs; Bronze records a completed dataset boundary and per-table acknowledgments. The cluster still uses its previous images until the owner releases v4.

For the Task 6 cutover, first ensure the Lakekeeper `raw` warehouse and its MinIO storage access exist, then publish the image/DAG release and initialize the v4 catalog. Catalog init adds only the four nullable v4 lineage columns to existing Bronze Iceberg tables in place; existing rows and table identities are preserved, while other schema conflicts still fail validation. The init DAG defaults to a destructive PostgreSQL `source` reset and new dataset baseline. For a non-destructive install on existing rows, trigger it with `{"source_init_mode":"journal_migrate"}`; those rows become one baseline and missing historical per-day changes cannot be recovered. The first future generator date is advanced past the latest existing order date. Generate the selected history in one backfill run, transfer Raw in bounded batches, and run the Bronze full-rebuild DAG once the complete source history is accepted. Keep Silver, Gold, and Curie handoffs disabled.

The daily publisher stages and tests models locally before changing Lakekeeper tables. Silver daily `fact_delivery_tracking` and `fact_order_product` inputs publish through three `order_id` ranges each, with keyed `MERGE` updates and inserts; target-only historical rows are preserved. Complete Silver dimensions and budgets use a keyed merge followed by deletion of keys absent from the complete source. Every Gold dbt model reads the full published Silver inputs and produces a complete aggregate snapshot in daily and full-history modes. Gold publication updates and inserts its keys, then removes keys absent from that snapshot. Empty complete sources fail before publication. Fact ranges commit independently, so a failed publish can leave earlier ranges applied; rerunning the DAG converges by replaying all ranges.

Silver and Gold layouts follow DuckDB Iceberg 1.5 write limits: they are unsorted, and Silver fact partitioning uses DuckDB-supported identity transforms. For partitioned writes DuckDB ignores the target-file-size property; weekly Spark housekeeping uses the contract size target when compacting those tables. Contract validation rejects Spark-only distribution modes and unsupported DuckDB transforms before initialization.

## Contract and catalog

[The canonical Iceberg contract](../tools/contracts/ampere_tables.json) contains v4: 16 Raw, 17 Bronze, 17 Silver, and 8 Gold tables. It defines Raw change keys, entity keys, operation semantics, before-images, source order, physical layouts, publication keys, and maintenance profiles. `tools/contracts/ampere_contract.py` validates and resolves these fields, and Spark conformance checks active partition and sort metadata. The contract and catalog image are prepared but not deployed. Catalog initialization requires the Raw Lakekeeper warehouse and its storage access. Bronze's current-state lineage includes dataset ID, stable source-row ID, batch sequence, and change ID. dbt models still define Silver and Gold transformations and tests.

To regenerate the diagrams and DAG inventory, run `uv run python tools/docs/generate_dataflow_docs.py` from the repository root.
